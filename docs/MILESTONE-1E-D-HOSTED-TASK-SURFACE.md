# Milestone 1E-D — Hosted task-surface adapter

## Goal

Make the existing user-facing task surface usable against the hosted D1 task model without rewriting the UI and without weakening workspace authorization, task visibility, recurrence, or atomicity semantics.

This milestone is a runtime/repository compatibility layer only. It does **not** create real Cloudflare resources, wire a production route, deploy the app, or migrate settings/reminders/live feeds.

## Baseline

Start from current `main` after Milestone 1E-C.

Work on:

`milestone/1e-d-hosted-task-surface`

Target PR:

`main`

## Existing contracts to preserve

### UI/local compatibility model

The current UI consumes `TaskItem` and `TaskMutationRepository`:

```ts
type TaskMutation =
  | { kind: "CREATE"; task: TaskItem }
  | { kind: "UPDATE"; taskId: TaskItem["id"]; task: TaskItem }
  | { kind: "DELETE"; taskId: TaskItem["id"] };

type TaskMutationRepository = {
  read(): Promise<TaskItem[]>;
  apply(mutations: TaskMutation[], now: string): Promise<TaskItem[]>;
};
```

Do not change the UI contract merely to make D1 easier.

### Hosted canonical model

D1 uses `HostedTask` and the existing deterministic workspace visibility rule:

- Personal task → Personal only
- Indelitech task → Indelitech + Personal roll-up
- Personal never appears in Indelitech

The compatibility layer must retain one-record truth. Never clone an Indelitech task merely because it is visible from Personal.

## Runtime-neutral mapping

Add a small runtime-neutral compatibility module, such as:

`lib/runtime/hosted-task-compat.ts`

It should provide focused mapping helpers between `HostedTask` and `TaskItem`.

Preserve all meaningful fields:

- ID
- primary workspace
- title
- context/description
- category
- project
- person
- type
- priority
- status / done
- due value and date-only semantics
- remindAt
- followUpAt
- duration label and numeric duration compatibility
- recurrence
- seriesId
- recurrenceAnchorDay
- dependency
- createdAt
- completedAt
- source
- sourceContext
- captureFingerprint
- updatedAt
- hosted-only fields such as `lastNotifiedAt` when updating an existing record

### Due values

Do not introduce UTC-midnight regressions.

- `YYYY-MM-DD` UI due → hosted date-only due.
- Empty UI due → hosted `null`.
- Hosted date-only due → UI `YYYY-MM-DD`.
- Hosted timestamp due → preserve a meaningful timestamp representation; do not silently truncate it to a date.
- Legacy `Today` should not be newly generated by the hosted adapter.

### Recurrence

- Hosted `null` recurrence maps to the UI's `One-time` convention.
- `Daily`, `Weekly`, and `Monthly` remain unchanged.
- Completed recurrence occurrences retain the same primary workspace as their parent series.

### Duration

Preserve exact UI labels:

`5m / 15m / 30m / 1h / 2h+ / Project`

Use hosted numeric minutes where meaningful, but do not lose `Project` merely because it has no precise minute value.

### IDs

The hosted/D1 model requires stable string task IDs.

Do not silently alias a numeric UI ID to a string if that can collide with an existing string ID. At the hosted mutation boundary, reject non-string IDs with a clear validation error unless a collision-safe migration rule already exists and is explicitly tested.

## Hosted D1-backed TaskMutationRepository

Add a D1-backed implementation of the existing `TaskMutationRepository` contract. A likely name is:

`D1TaskMutationRepository`

It should be constructed with:

- D1 database/repository dependencies;
- an already-authorized `RequestContext` for the viewing workspace.

`read()` returns the visible D1 tasks mapped to canonical `TaskItem`s.

`apply()` must apply the mutation batch atomically and return the resulting visible task snapshot.

### Required atomicity

Use a single D1 transaction/batch for a mutation batch. Do not perform mutation-by-mutation independent commits.

If any operation fails, no operation in that mutation batch may persist.

This is particularly important for recurring completion.

## Mutation semantics

### CREATE

Normal create is permitted only when the new task's primary workspace equals the authorized workspace.

Visibility is derived from the existing deterministic policy; clients do not choose arbitrary visibility rows.

Do not allow Personal to create arbitrary Indelitech tasks merely because Personal can see rolled-up Indelitech records.

### UPDATE

A visible Indelitech task may be updated from the Personal roll-up, and that update must modify the same D1 task row.

Preserve immutable hosted metadata:

- primary workspace
- createdAt
- an existing non-null capture fingerprint

Also preserve hosted-only values not represented by the UI, especially `lastNotifiedAt`.

### DELETE

Support real permanent delete for a task visible to the authorized workspace.

Deleting a rolled-up Indelitech task from Personal deletes the same record, not a Personal copy.

Rely on/ensure foreign-key cleanup of `task_visibility` rather than leaving orphan visibility rows.

### Recurring completion from Personal roll-up

This is a required acceptance case.

Completing a visible Indelitech recurring task from Personal currently produces two logical mutations:

1. CREATE a DONE occurrence whose primary workspace remains `indelitech` and whose `seriesId` references the parent series;
2. UPDATE the existing Indelitech series to its next due date.

Normal cross-workspace CREATE must still be denied. Therefore add only the narrow rule required for this recurrence transition:

- caller is authorized for Personal;
- parent series is visible to Personal;
- parent is actually Indelitech-owned and recurring;
- created occurrence is DONE;
- occurrence `seriesId` matches that parent task ID;
- occurrence retains the parent's primary workspace;
- parent UPDATE is in the same mutation batch;
- the whole CREATE + UPDATE is atomic.

Do not turn this into a general permission for Personal to create Indelitech tasks.

## D1 repository support

The existing `HostedTaskRepository` lacks delete and is oriented around single operations. Extend or add internal D1 mutation support only as much as necessary to implement this milestone correctly.

Avoid duplicating visibility policy. Reuse `taskVisibleInWorkspace` and current D1 schema constraints.

Do not regress the structured-capture service or its repository behavior.

## Hosted workspace response adapter

Add a small hosted workspace-read service/adapter capable of producing the task portion of the current UI bootstrap shape:

```ts
{
  tasks: TaskItem[];
  reminders: [];
  initialized: true;
  legacyBrowserImportAllowed: false;
}
```

For this milestone, hosted reminders are intentionally empty. Do not fake reminder migration.

Do not wire `/api/workspace` to this adapter yet; route/runtime cutover belongs to the next milestone.

## Explicitly deferred

- production `cloudflare:workers` route imports;
- real D1 database creation/binding;
- real Cloudflare Access app/policy;
- production workspace grant seeding;
- production deploy;
- hosted settings migration;
- hosted reminders migration;
- live/news/brief hosted cutover;

- Telegram notifications;
- Google Calendar sync.

## Required regression coverage

At minimum cover these behaviors:

1. TaskItem → HostedTask metadata mapping.
2. HostedTask → TaskItem metadata mapping.
3. Date-only due round-trip.
4. Timestamp due is not silently truncated.
5. Empty due ↔ null.
6. Exact duration labels round-trip, including `Project`.
7. Existing `lastNotifiedAt`, capture fingerprint, and createdAt survive UI-style update.
8. Non-string hosted mutation IDs fail closed.
9. Personal read returns Personal + Indelitech roll-up exactly once each.
10. Indelitech read excludes Personal tasks.
11. Personal create creates Personal ownership/visibility only.
12. Indelitech create rolls up to Personal.
13. Personal can update a rolled-up Indelitech task without cloning it.
14. Personal can permanently delete a rolled-up Indelitech task without leaving visibility rows.
15. Arbitrary Personal → Indelitech create is denied.
16. Recurring completion from Personal creates a DONE Indelitech occurrence and advances the same Indelitech series.
17. Recurring occurrence and parent update commit atomically.
18. Forced failure in that batch rolls back both changes.
19. Capture fingerprint remains immutable.
20. Primary workspace remains immutable.
21. createdAt remains immutable.
22. Hosted workspace response is initialized, disables legacy import, and returns `reminders: []`.

Preserve all existing recurrence, D1 visibility, structured-capture, Access/session, and vinext tests.
